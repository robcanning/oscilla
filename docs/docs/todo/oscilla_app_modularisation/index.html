Oscilla app.js Modularisation – Implementation Plan

This document outlines a practical, low‑risk plan for cleaning and modularising app.js in Oscilla. The goal is to reduce cognitive load, isolate responsibilities, and make future debugging (especially sync / speed / playhead issues) easier, without breaking runtime behaviour.

Guiding Principles

  • One responsibility per module (transport ≠ network ≠ UI ≠ SVG init)
  • Avoid circular imports by keeping app.js as the orchestrator
  • Prefer thin glue in app.js, thick logic in modules
  • Preserve existing globals initially; refactor state later

Target Folder Structure

public/js/
├── app.js                     # orchestration only
├── oscillaSocket.js            # WebSocket + protocol
├── oscillaClients.js           # client list + audio master
├── oscillaUIBindings.js        # DOM + keyboard wiring
├── oscillaSVGInit.js           # SVG settle + layout + inject
├── oscillaPaths.js             # path variants + helpers
├── oscillaRAF.js               # RAF loop + tick pipelines
├── oscillaProjectMenu.js       # project list + menu
└── (existing modules)

Module Breakdown

1. oscillaSocket.js

Responsibility: network transport and message routing

Move from app.js:

  • getWebSocketURL()
  • connectWebSocket() and reconnect logic
  • socket.addEventListener("message", …) switch / routing
  • outbound message helpers (score_meta, cuePause_ack, etc.)

Exports:

connectSocket()
sendSocketMessage(type, payload)
setSocketEnabled(bool)
getSocket()

Notes:

  • Do not import UI or transport here
  • Use callbacks or events to notify app.js

2. oscillaClients.js

Responsibility: multiplayer presence + audio‑master state

Move from app.js:

  • updateClientList()
  • client list click → rename logic
  • audio master toggle + UI update
  • window.isAudioMaster getter/setter

Exports:

initClientUI()
updateClientList(clients)
setAudioMaster(state)

3. oscillaUIBindings.js

Responsibility: DOM event wiring only

Move from app.js:

  • DOMContentLoaded UI listeners
  • fullscreen toggle
  • keybindings popup
  • hamburger / menu select handling
  • keyboard shortcuts
  • score notes toggle

Exports:

initUIBindings()

Rule: no business logic here — call into app.js or other modules

4. oscillaSVGInit.js

Responsibility: SVG setup lifecycle

Move from app.js:

  • initializeSVG(svgElement)
  • page vs scroll mode branching
  • wide scroll layout logic
  • settleDomForPropagate()
  • scroll disabling / layout measurement

Exports:

initializeSVG(svgElement)

Notes:

  • Keep window.initializeSVG = initializeSVG if globals are needed
  • This module should not know about WebSockets

5. oscillaPaths.js

Responsibility: path variants and helpers

Move from app.js:

  • window.pathVariantsMap
  • storePathVariants(svgElement)
  • ensureWindowPlayheadX() (optional)

Exports:

storePathVariants(svgElement)
getPathVariants(id)

6. oscillaRAF.js

Responsibility: runtime animation heartbeat

Move from app.js:

  • window.animate
  • window.startAnimation() / stopAnimation()
  • RAF loop iterating window.runningAnimations
  • frame‑based checks:
    • impulse regions
    • synth regions
    • speed triggers

Design improvement: Use a pipeline list instead of hard‑coded calls.

Exports:

initAnimationLoop({ pipelines })
startLoop()
stopLoop()

7. oscillaProjectMenu.js

Responsibility: project discovery UI

Move from app.js:

  • populateProjectMenu()

Exports:

populateProjectMenu()

What Stays in app.js (for now)

  • Global playback state (isPlaying, playheadX, speedMultiplier)
  • Cross‑module wiring (socket → transport → UI)
  • window.* bindings used by legacy code
  • Startup order:
    1. load project
    2. initialise SVG
    3. assign cues
    4. start observer
    5. connect socket

Later refactor: collapse globals into a shared state object.

Recommended Extraction Order (Low Risk → High Value)

  1. oscillaProjectMenu.js
  2. oscillaPaths.js
  3. oscillaUIBindings.js
  4. oscillaClients.js
  5. oscillaSocket.js
  6. oscillaSVGInit.js
  7. oscillaRAF.js

This keeps behaviour stable while steadily shrinking app.js.

Expected Outcome

  • app.js reduced to an orchestration layer
  • Clear boundaries between network, UI, SVG, and runtime
  • Easier debugging of sync / speed / playhead issues
  • Safer future refactors (OSC inputs, feedback routing, param coupling)

This plan intentionally prioritises clarity and stability over architectural purity. Further refactors (state container, event bus, dependency inversion) can happen once the modules are in place.
