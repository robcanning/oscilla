Feature: Drop Marker (Implementation Specification)

Overview

The Drop Marker feature allows performers to place shared, temporary structural markers directly onto the score during rehearsal or performance. Markers are rendered as vertical HTML overlay lines, clipped to the score height, and persisted via the existing Contribution Surface annotation system.

Markers are:

  • dropped at the current playhead position
  • shared by default
  • draggable via their label
  • nameable
  • saved and restored with annotation JSON

Markers function as live rehearsal structure and may later act as navigation jump targets (Phase 2).

Scope

Phase 1 (this specification)

  • Marker creation
  • Rendering as score-clipped overlays
  • Dragging via label
  • Label editing and deletion
  • Persistence and network sharing via annotation system

Phase 2 (out of scope, reserved)

  • Integration into rehearsal / navigation jump lists
  • Marker-based jump / seek behaviour

Creation

Trigger

  • UI button: “Drop Marker”
  • (Optional later) gesture input

Creation logic

On trigger:

  1. Read window.playheadX (authoritative playhead position).
  2. Create a new annotation item with:
    • kind: "marker"
    • scope: "shared"
    • placement.x = window.playheadX
  3. Insert the item using the same annotation add pipeline used for standard annotations.

No pointer or DOM position is consulted.

Data Model

Markers are stored as standard annotation items inside state.items.

{
  id: "ann_<uid>",
  kind: "marker",
  text: "Marker",
  scope: "shared",

  createdAt: <timestamp>,
  updatedAt: <timestamp>,

  anchor: {
    mode: "scroll" | "page",
    pageId?: "page_<id>"   // required only when mode === "page"
  },

  placement: {
    space: "score",
    x: <number>,
    y: 0
  }
}

Notes

  • placement.x is the only mutable spatial parameter.
  • placement.y is fixed and not user-editable.
  • Marker height is not stored; it is derived from CSS and container bounds.
  • text is used as the marker label.

Rendering

DOM structure

Markers are rendered into the same score overlay container used by annotations.

<div class="osc-marker" data-id="ann_123">
  <div class="osc-marker-line"></div>
  <div class="osc-marker-label">A</div>
</div>

Styling (CSS-only)

All visual styling must live in style.css.
No inline styles are permitted.

Required CSS contract:

.osc-marker {
  position: absolute;
  top: 0;
  pointer-events: none;
}

.osc-marker-line {
  position: absolute;
  top: 0;
  bottom: 0;          /* clipped to score container height */
}

.osc-marker-label {
  position: absolute;
  top: 30px;          /* default grab-handle position */
  pointer-events: auto;
  cursor: grab;
  user-select: none;
}

Visual appearance (color, opacity, font, hover states) is expected to be overridden later via user.css.

Clipping & Layout Rules

  • Marker line height is always clipped to score height.
  • Viewport-height or playhead-following markers are explicitly disallowed.

Scroll mode

  • Marker spans full SVG score height.

Page mode

  • Marker is rendered only when anchor.pageId matches the active page.
  • Marker height equals the page height.

No special height metadata is stored.

Interaction

Dragging

  • The label is the sole drag handle.
  • Dragging updates:
    • placement.x
  • Dragging does not modify:
    • height
    • y-position
    • anchor or scope

On drag end:

  • Persist changes via the existing annotation update pipeline.

Editing

  • Clicking the label opens a minimal editor:
    • Single text input for label
    • Delete button
  • Saving updates text.
  • Deleting removes the annotation item.

No trigger, audio, or cue UI is exposed for markers.

Persistence

Markers are persisted exactly like other annotations:

  • Stored in localStorage
  • Included in annotation export JSON
  • Restored on import
  • Merged by id

No schema changes or version bumps are required.

Networking

Markers default to scope: "shared" and therefore:

  • Are broadcast via existing annotation WebSocket sync
  • Are hydrated automatically for late-joining clients

No new message types are introduced.

Phase 2 (Reserved): Navigation Integration

Markers may later act as navigation / jump targets.

Planned behaviour:

  • Marker entries appended to rehearsal / jump list
  • Sorted by placement.x
  • Jump action scrolls to placement.x
  • In page mode: switch page, then scroll

Phase 2 must not modify the Phase 1 data model.

Acceptance Criteria (Phase 1)

  • “Drop Marker” places marker at window.playheadX
  • Marker line is clipped to score height
  • Label appears 30px from top
  • Label drag moves marker horizontally
  • Label is editable
  • Marker persists across reload
  • Marker syncs across clients
  • No inline styles are used

Non-Goals

  • Viewport-height markers
  • Pointer-based drop positioning
  • SVG-authored marker export
  • Audio, cue, or trigger behaviour
